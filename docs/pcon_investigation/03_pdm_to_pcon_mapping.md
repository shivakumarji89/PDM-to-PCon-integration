# 03 — PDM ↔ pCon Concept Mapping

**Status:** Forensic, evidence-only. No code changed. This file synthesizes the two prior
investigation tracks — `01_pcon_creator_2_22_2_investigation.md` (pCon.creator manual),
`09_mdf_export_import_requirements.md` (import/export contract — "MDF" does not exist as a
term; the real formats are OCD/XOCD/XCF/MDB/EBASE), `02_mdb_structure_and_relationships.md`
(current MK Workbench exporter code), and `07_relation_object_configuration_model.md`
(relation model) — against the PDM legacy baseline
(`docs/Legacy_PDM_Business_Logic/05_Products.md`, `06_Articles.md`, `07_Attributes.md`,
`08_Property_Values.md`, `09_Options.md`, `10_Option_Values.md`, `11_Configuration.md`,
`26_Data_Model.md`) and the PDM→MDB generator docs (`docs/PDM_MDB_Engineering/02_PDM_Data_Model.md`,
`03_Engineering_Object_Mapping.md`).

**Labels:** **FACT** (directly documented/observed), **INFERENCE** (derived, not itself
written down), **UNKNOWN** (insufficient evidence). Per the task brief: do not invent a
mapping just because names are similar — where a PDM concept has no pCon.creator
counterpart, that is stated explicitly rather than papered over.

## Key non-mappings (explicit, not papered over)

1. **PDM Option → pCon "Option" does not exist.** pCon.creator has no dedicated Option
   concept; PDM's Option (a real, DB-backed, dependency/exclusion-bearing entity — see
   file 06) collapses entirely into pCon's Property/PropertyValue with `Usage=Configuration`.
   Any migration plan that assumes a target `tCOMd_Option` table is a live write target is
   wrong for the current OCD-consuming pipeline: neither the legacy PDM exporter (`OCDExport.cs`,
   confirmed by `docs/pcon_reference/OCDTables.md`/`03_Engineering_Object_Mapping.md`) nor the
   current MK Workbench exporter writes it (**FACT**, file 02 §1).
2. **PDM Relation-object equivalents do not exist as a single table** — PDM's nearest
   analogues are five/six different mechanisms (`DependentAttributeValues`,
   `DependentOptionValues`, `AttributeValueExclusions`, `CatalogueProductOptionExclusions`,
   `CatalogueItemOptionExclusions`) that map onto a **mix** of pCon Relation Object types and
   Constraint value-combination tables — never a clean 1:1. See file 06 for the full breakdown.
3. **PDM has no "Base Article"/"Variant"/"Configuration" tables** — all three are structural
   inferences (head/tail SKU decode, article-set co-occurrence) rather than named PDM schema
   objects. See file 04/05 for the detailed treatment.
