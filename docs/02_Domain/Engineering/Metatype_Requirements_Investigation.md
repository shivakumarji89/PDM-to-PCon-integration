## 3. Intended end-to-end workflow

**Authoritative process (template, read in full; PROJECT PROCESS FACT).** The template is a prompt for an AI assistant run inside the series repo: one question per step, no file edits until Step 6 is confirmed.

1. **Read repository/series data first.** Inspect `go_types.csv` (naming pattern, prefixes, flags), `go_propvalues.csv` and `go_proporder.csv`, `go_children.csv`, and any in-series `docs/*.md`. "If the target series has few or no existing Metatype examples" also check `hmx/atlas`, `hmx/pullman` and `hmx/layout`. Summarise briefly before Step 2.
2. **Ask which kind of Metatype:** Polymorphism Metatype (article substitution driven by a property value, no parent/child) or Metatype with Childs. Wait for the answer.
3. **Property name:** technical name (`GATLAS_…` / `GPULLMAN_…` style, matching the series' prefix) and English label.
4. **Branch by pattern.** Polymorphism: which articles are switched, whether unconditional or scoped, whether every article accepts every value. Childs: the child-defining property, its label and values, per-value child articles, optional positioning.
4a. **Value validity per article**, value by value. Usually a per-article whitelist in `go_propvalues.csv`; warn about a `go_propvalues` filter that contradicts a `go_actions` enable/default gate.
5. **Translations, always last:** German, French, Dutch (English already given), confirmed as a table.
6. **Confirmation, then implementation:** edit `go_types, go_propvalues, go_proporder, go_children, go_actions` "etc." following the series' conventions.

**Build (Verus prompt only, not in the template).** `cd hmx/<series>/1; ebmkdb.exe mt.inp_descr <series>.ebase`; never `make_ebase.bat` (it contains `pause`); success = exit code 0 and a fresh `.ebase` timestamp.

## 5. Assessment of the Repository Scanner and Table Loader

- **They are needed, and in the right order.** They provide the data access that Step 1 uses; Step 1 and Step 2 are built on them.
- **Build status is a heuristic.** `_classify` returns BUILT when `mt.inp_descr`, a non-empty `.ebase`, populated `go_types`/`go_articles` and all declared non-optional tables exist. It ignores timestamps (`SCAN_POLICY`) and never opens the `.ebase`. OBSERVED: `oe1/1` has `oe1.ebase` dated 2026-08-12 while `odb.ebase` is 2026-07-01, so timestamps alone are ambiguous. A BUILT label means "build artefacts exist", not "valid or current".
- **The loader is a faithful raw reader.** Its `DECODE_ERROR` on 40 `go_texts.csv` files describes the app's strict-UTF-8 policy, not necessarily a data defect (§7).

## 6. Assessment of the Relationship Resolver

- **Authorisation:** requested by the owner on 2026-10-14. It is not a pre-existing or unrequested component.
- **What it checks:** `articles.id→types.id`, `articles.chprm_key→childprops.key`, `childprops.child_key→children.child_key`, `childprops.name→types.name`, `properties/propvalues/propclasses/setup/classes/attpt/actions.id→types.id`, `actions.own_key→types.name`, `actions.foreign_key/param_2→children.child_key`, `types.filter→types.name`, plus duplicate-key checks. `articles.prm_key→properties.key` is marked "observed" only (the manual contradicts itself, lines 1136 vs 1195). `go_texts` is deliberately not checked.
- **Relation to the template:** Steps 1-2 do not use it. It serves the later checks the template implies (Step 4a's reachability warning) and generated-row validation.
- **OBSERVED on real data (read-only run over the 49 built families):** 15 reports `ok`, 34 `issues`. Core links resolve fully (`articles.id→types.id` 820 of 820). Several rules fire often, e.g. `actions.own_key→types.name` 257 unresolved, `propclasses.prop_name→types.name` 66 across 30 families. Samples look like genuine inconsistencies (e.g. a property used in filters but never defined), but `propclasses.prop_name` may be over-strict (native properties). **Unverified:** whether the severities and rules match practice. This needs review by someone who knows OFML before the resolver's output is treated as authoritative.
- **Risk:** the resolver is uncommitted and consumed only by the diagnostic page.
